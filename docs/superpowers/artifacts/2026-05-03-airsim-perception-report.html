  • UE-rendered warehouse interior + ray-traced depth map confirmed working from a drone-attached forward-facing camera

  • Camera ingestion is gRPC, not MAVLink — distinct from COR-94/COR-98 transport stack, documented for the team

Gotchas

  • simGetImages RPC takes ~333 ms per call (RGB + depth) — observed throughput is ~3 Hz, not the 10 Hz target. Bottleneck is the AirSim → Python image transfer, not our processing
  • SimpleFlight's moveToZAsync + 5 s wait barely lifted the drone (~0.5 m). Switched to issuing rotateByYawRateAsync which holds altitude internally; that worked. Lesson: AirSim's high-level move APIs are reliable; mixing with low-level body-rate commands cancels altitude hold
  • Depth from DepthPerspective is Euclidean ray length, NOT planar Z-buffer. Must convert before TSDF integration — formula z_planar = depth_euclidean · cos(pixel_angle) per COR-92 step 9
  • Cosys-AirSim's RGB buffer is BGR (3 bytes/pixel), not BGRA (4 bytes/pixel) like older Microsoft AirSim docs claim. Detect channel count at runtime, swap to RGB after
  • Drone never reaches AirSim's nominal 3 m takeoff altitude on this UE setup — settles around 1.2 m. Likely SimpleFlight throttle limits or UE collision response. Doesn't block M3 MVP

Barriers

  • None — M3 MVP fully achieved; perception arc unblocked

Context

Why this matters

COR-99 validated AirSim integration plumbing on Windows-native UE 5.5.4 + Cosys-AirSim. M3 is the actual reason we did M2: get UE-rendered camera frames into our perception pipeline so the GateNet / depth-mapping work for the DCL competition has a known-good baseline. PyBullet renders are too primitive for serious GateNet evaluation; UE's photoreal warehouse interior is the right test bed.

Per the project_perception_complexity memory: gate detection alone isn't enough — we also need local depth/occupancy mapping for collision avoidance. AirSim's simGetImages exposes both RGB and depth synchronously, so this milestone covers both data sources in one call.

Technical background

  • Two transport stacks now in our codebase: MAVLink (UDP/14550) for policy ↔ numpy_quad (COR-94/COR-98), and gRPC/msgpack-rpc (TCP/41451) for policy ↔ AirSim (COR-99/COR-100). Both validated end-to-end, both Windows-native.
  • SimpleFlight: AirSim's built-in flight controller. Communicates via gRPC, exposes telemetry, action commands, and rendered images through a single cosysairsim.MultirotorClient.
  • BP_FlyingPawn ships with 5 default rigid-mounted camera child actors (forward, side, back, bottom). No settings.json camera overrides needed for M3.

Setup

  • UE Editor + plugin
    UE 5.5.4 + Cosys-AirSim plugin v3.4.0 (already built into DroneSim project from prior work; MSVC 14.38 toolchain).
  • AirSim runtime
    Press Play in Editor with AirSimGameMode. Auto-spawns SimpleFlight vehicle from ~/Documents/AirSim/settings.json on Windows.
  • Python client
    cosysairsim 3.3.0 in monorace conda env on Windows. Connects to AirSim's localhost:41451.
  • Camera config
    Default — no Cameras block in settings.json. Uses BP_FlyingPawn's built-in cameras at 144×256 each.
  • Recording target
    10-second recording at 5 Hz (~3 Hz achieved due to RPC bandwidth). Drone takes off + rotates in place at +0.8 rad/s yaw rate so the camera sweeps the warehouse.

Execution

  1. 1
    Camera ingestion: get_camera_images() on AirSimPolicyClient
    Wraps simGetImages([ImageRequest(camera, ImageType.Scene/DepthPerspective)]). Returns RGB as (H, W, 3) uint8 in RGB channel order + Depth as (H, W) float32 in meters along ray. Includes capture-time camera pose from ImageResponse.camera_position/orientation (NOT simGetVehiclePose, per COR-92 step 9 — those drift up to 0.43 m apart from the actual capture pose).
  2. 2
    Camera-name probe
    Wrote scripts/airsim/_probe_cameras.py to enumerate which camera handles AirSim accepts on the SimpleFlight vehicle. All 5 standard names (front_center, front_right, front_left, back_center, bottom_center) returned 144×256 RGB + Depth frames. Numeric and empty-string names also work as fallback aliases.
  3. 3
    Frame recorder + rerun blueprint
    scripts/airsim/_record_frames.py connects to AirSim, optionally takes off + commands a yaw rotation, pulls synchronized RGB + depth + telemetry per tick, and logs to a self-contained .rrd file. Blueprint pattern reused from COR-97's replay viz: 4 panels (3D orbit, RGB, Depth, scalar plots) baked in via rrb.Blueprint so the viewer opens straight to the layout.
  4. 4
    Motion + altitude debugging
    First attempt: send_action([0,0,0,yaw]) via our env-style body-rate path. Drone fell back to ground after takeoff — throttle=0.5 isn't enough for SimpleFlight hover, AND body-rate commands cancel AirSim's altitude hold. Pivoted to AirSim's high-level rotateByYawRateAsync (handles altitude automatically). Final config: moveToZAsync(-3 m) for altitude target + rotateByYawRateAsync for the recording window. Drone reaches ~1.2 m (not 3 m) but holds altitude during rotation.
  5. 5
    Visualization tuning
    Initial 3D orbit view looked empty — drone body axes were 30 cm and sphere was 10 cm radius, invisible at default zoom. Bumped to 1 m axes + 0.5 m sphere + added a 2 m world-origin reference frame. Drone now visible at any orbit angle.

Throughput

  • Effective FPS: ~3 Hz (target was 5 Hz). Bottleneck is the simGetImages RPC round-trip — ~333 ms per RGB+Depth pair at 144×256.
  • For GateNet: 3 Hz is workable for offline eval. Closed-loop perception (M5+) would need either lower resolution, RGB-only, or batched calls.
  • For depth-to-TSDF integration (overlap with Janahan's COR-91): 3 Hz keyframes are fine.

Takeaways & Decisions

GO

Adopt this stack as the perception bring-up baseline. AirSimPolicyClient.get_camera_images() + the rerun recorder are the foothold for the GateNet / depth-mapping arc.

NO-GO (this issue)

Don't attempt closed-loop perception (PnP feeding the policy obs) yet. That's a separate research arc and depends on the GateNet model itself, which doesn't exist for our visual conditions yet (per project_perception_complexity).

Analysis

  • Camera transport is gRPC, not MAVLink. Two transport stacks in the codebase now — MAVLink for policy/numpy_quad (COR-98), gRPC for policy/AirSim (COR-99/100). Both Windows-native. Future closed-loop work picks per environment.
  • Depth quality is the headline finding. The depth map cleanly shows shelving distance + open-door void with a useful gradient. This is the data Janahan's TSDF / DepthAnything work (COR-91/COR-93) needs — we can now feed AirSim depth directly into that pipeline.
  • RGB photoreal-ness is sufficient for GateNet evaluation. Lighting + texture in the warehouse interior are recognizable; this is the right test bed once we have a GateNet model. PyBullet renders would have been useless for that.
  • Throughput is the open question for closed-loop work. 3 Hz at 144×256 means ~330 ms latency per perception cycle. Acceptable for offline eval; tight for real-time control. Mitigations: lower res, RGB-only, batched calls.
  • SimpleFlight altitude controller is throttle-limited on this UE setup — reaches ~1.2 m instead of the 3 m target. Doesn't block perception work but worth knowing. Likely SimpleFlight defaults or UE collision response.
