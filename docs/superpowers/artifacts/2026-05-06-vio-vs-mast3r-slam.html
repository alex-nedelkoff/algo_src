VIO vs MASt3R-SLAM — TL;DR + side-by-side

Two fundamentally different approaches to "where am I in the world" for a racing drone. VIO is the 30-year classical recipe; MASt3R-SLAM is a 2024 foundation-model approach. Picking between them depends on what you optimize for.

30-second TL;DR

VIO (Visual-Inertial Odometry) = "track sparse image features + integrate IMU + optimize the chain." A camera sees corners / blobs in the scene; the IMU integrates motion at 200 Hz; an EKF or factor graph fuses the two, outputting 6-DoF pose at 100+ Hz. classical CPU 100 Hz drifts on bad textures

MASt3R-SLAM = "feed two images into a transformer, get dense pixel correspondences + 3D points in a unified frame, run SLAM on top." The transformer (MASt3R, 2024) replaces the entire feature-matching front-end with one foundation-model pass. 2024 GPU ~15 Hz handles textureless scenes

Both produce 6-DoF pose as the primary output. MASt3R-SLAM also produces a dense 3D map as a free side effect (because the foundation model already predicts 3D points). VIO usually outputs a sparse landmark map — useful for loop closure, not for cost-map planning.

Side by side

VIO — what it is

30+ years of accumulated engineering. The recipe:

  • Detect sparse image features (FAST, ORB, SuperPoint).
  • Match them across frames with descriptor distance.
  • Triangulate 3-D landmarks; track them.
  • Integrate accelerometer + gyro between camera frames (IMU pre-integration).
  • Solve a factor graph or EKF that minimizes reprojection error + IMU consistency.
  • Output: drone pose at every IMU update (200+ Hz typically).

Best-in-class implementations: ORB-SLAM3 (visual-inertial), VINS-Fusion, OpenVINS, MSCKF.

Failure mode: textureless walls, repetitive patterns (warehouse rack labels!), rapid motion blur. Sparse features run out of distinctive matches.

MASt3R-SLAM — what it is

A 2024 paper (Murai et al.) that wraps a foundation model into a SLAM system. The recipe:

  • Take two RGB frames; pass them through MASt3R (a ViT-based transformer).
  • The model outputs dense per-pixel correspondences AND per-pixel 3-D points in a shared frame — feed-forward, no iterative matching.
  • Aggregate per-frame predictions into a global map; estimate pose by aligning new frames to the map.
  • Loop closure and relocalization fall out of the same matcher.

Best-in-class: MASt3R-SLAM is itself the leading example. DUSt3R (the predecessor) is what you'd compare against.

Failure mode: compute. The MASt3R forward pass is ~50–100 ms on a recent GPU; SLAM rate is bounded by that. Not real-time on Jetson without quantization. Camera-only; ignores IMU (some forks add it).

For our racing drone, why MASt3R-SLAM

Three things about our setup push toward MASt3R-SLAM specifically:

  1. Static map known from exploration phase. We don't need to build the map online — we already have it (Janahan's TSDF / mesh). MASt3R-SLAM's "register a new frame against a known map" mode is a single transformer pass, no incremental SLAM optimization needed.
  2. Warehouse interior is texture-poor and repetitive. Long bare walls, identical shelving, similar columns. Classical VIO front-ends (corner detectors) struggle here. The MASt3R transformer is much more robust to these conditions.
  3. The architecture call from M1 is "ICP at 1 Hz against the static map." MASt3R-SLAM literally is "transformer-based ICP at 10–20 Hz against the static map." Same architectural slot, much stronger frontend. Slots into the existing M5 closed-loop demo as a drop-in replacement for our open3d ICP.

The cost we're accepting: 50–100 ms / frame compute, GPU-only inference, ~1.5–2 hr install. The qualifier sim runs on the dev box (RTX-class GPU available), so the compute cost is fine — we're not yet on Jetson.

What we lose by not using VIO

Two things to be honest about:

  • No IMU integration in MASt3R-SLAM. Pose update rate is 10–20 Hz, not 100 Hz. We'd interpolate between MASt3R updates with IMU integration if we want 100 Hz pose for the policy. (The policy runs at 100 Hz; the planner at 5–10 Hz; if we feed the policy IMU-only between vision updates, M1's drift numbers say we're fine within 0.1 s windows.)
  • Less mature. If MASt3R-SLAM hits an edge case in our simulator we haven't tested (e.g., the synthetic warehouse mesh produces depth gradients the foundation model wasn't trained on), recovery is harder than for a 15-year-mature ORB-SLAM3.

Mitigation: we keep our open3d ICP as a fallback. If MASt3R-SLAM doesn't work cleanly within the install + integration budget, fall back to ICP + improved initial-guess strategy (predict-then-correct, translation-only refinement).

Install plan in flight

  1. Clone repo + submodules into external_packages/MASt3R-SLAM
  2. Install Python deps in the existing monorace conda env
  3. Download MASt3R model checkpoints (~1 GB)
  4. Build CUDA extensions for the Gaussian-splatting backend if needed (we can run pose-only and skip this if it gives Windows trouble)
  5. Smoke-test: feed a single warehouse frame to MASt3R, verify the pose output looks sane
  6. Wire into the M5 closed-loop demo as a drop-in replacement for IcpLocalizer

Realistic budget: 1.5–2 hr if smooth, up to 3 hr if Windows quirks. Each step's logs land in outputs/perception/mast3r_install.log so if anything breaks we know exactly which dep choked.
