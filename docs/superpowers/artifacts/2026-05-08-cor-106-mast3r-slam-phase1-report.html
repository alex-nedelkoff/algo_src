MASt3R-SLAM Phase 1 — Cloud-Portable Visual Localization

2026-05-08 · branch cor-106-mast3r-slam-cloud-phase1 · target: RunPod RTX 3090

TL;DR

Wins

  • MASt3R-SLAM stack builds end-to-end on Windows + Linux: lietorch, mast3r_slam_backends, ViT-Large checkpoint loads (688.6M params)
  • Mast3rLocalizer wraps FrameTracker + SharedKeyframes, with one-shot env←slam alignment from frame-0 truth pose
  • Procedurally textured 14×10×3 m room from 4 Polyhaven CC0 PBR materials — drops in for the unrendered warehouse mesh, gives MASt3R-SLAM photoreal-ish features
  • Standalone smoke-test script: scripted oval flight, dual ICP-vs-MASt3R-SLAM, rerun web viewer
  • Cloud-portable repo + 4-script bootstrap workflow (apt deps, MASt3R-SLAM clone, curope build, checkpoint, asset gen, import smoke). Deploy-to-running in ~10 min on a fresh pod

Gotchas

  • Windows MSVC long is 32-bit but PyTorch index tensors are int64_t — patched long→int64_t in two MASt3R-SLAM CUDA kernels
  • Conda CUDA toolkit lives at <env>/, not <env>/Library/ — torch's _check_cuda_version probes $CUDA_HOME/bin/nvcc and dies with opaque WinError 2
  • MASt3R-SLAM expects multiple pip install -e thirdparty/* calls (mast3r, dust3r, in3d, asmk, curope), not just the root — import mast3r fails otherwise
  • mp.Manager() + CUDA spawn hangs indefinitely on Windows; wrote a threading-only _SingleProcessManager shim
  • RunPod rotates PyTorch templates; pinned torchvision==0.20.1+cu121 didn't match — bootstrap now detects host torch and pulls matching wheel

Barriers

  • 4 GB local GPU + Windows allocator (no expandable_segments) fragments at ~60 % model load → OOM. ViT-Large MASt3R-SLAM is fundamentally not deployable here
  • Decision: pivot to RunPod RTX 3090 24 GB. Linux build path also enables curope CUDA RoPE2D extension (Windows fell back to slow Python RoPE)

Context

AI Grand Prix's virtual qualifier doesn't publish drone pose — localization is a competition-relevant problem, not a free signal. Two candidate approaches were on the table:

  • ICP-against-mesh: cheap, no learning, but requires a depth sensor (or depth net) and a known map
  • MASt3R-SLAM (Murai et al. 2024): foundation-model SLAM, RGB-only, builds its own pointmap. Heavier but matches the on-board sensor stack

Phase 1 validates that each can track on PyBullet-rendered RGB before closing the loop with the policy. The textured-room asset isolates the localizer from MASt3R-SLAM's other failure mode (texture-poor flat-shaded CAD meshes are out-of-distribution for the foundation model).

Takeaways & Decisions

Go

Cloud GPU for MASt3R-SLAM dev

RTX 3090 24 GB on RunPod removes every Windows-specific workaround (allocator fragmentation, curope build, mp.Manager hang) and matches the deployment target's GPU class. ~$0.40/hr; Phase 1+2 estimated total ~$5.

Go

Phase 2: dual-rep splat + mesh from same video

Same-source 3DGS splat (RGB rendering for SLAM) + VDA-fused mesh (depth, collision) trivializes the alignment problem. Real captured environments give MASt3R-SLAM in-distribution input. Sim-to-real story collapses out for free.

No-Go

ViT-Large MASt3R-SLAM on 4 GB Windows GPU

The Windows CUDA allocator lacks expandable_segments; even with model-first ordering and in-place parameter moves, fragmentation kills the load. Not solvable without architectural changes (model split, fp16 with autocast surgery) that don't pay off vs. just using a bigger GPU.

No-Go

Vendoring MASt3R-SLAM in algo_src

Source is ~500 MB + 2.75 GB checkpoint. Not worth the repo bloat. Bootstrap clones upstream, applies our minimal patches via the platform-conditional setup.py. Rebuilds reproducibly from a clean pod.
