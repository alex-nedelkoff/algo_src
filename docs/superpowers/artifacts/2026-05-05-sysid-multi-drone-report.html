SysID Multi-Drone Capability Demo

Grey-box drone parameter identification across 4 drone classes spanning ~185× mass + 10× arm-length (Phase 1), plus a model-mismatch demo against drag-bearing data (Phase 2). Fit via PyTorch Adam on K-step rollout MSE.

Date: 2026-05-05  |  Branch: autoresearch-mvp

TL;DR

Wins

  • Pipeline scales cleanly across 4 drone classes (27 g → 5 kg) — same hyperparameters, no per-drone tuning.
  • Constrained fit (mass + arm pinned, the realistic competition scenario where organisers publish nominal specs) drops worst-case error and converges to a smaller training loss on every drone.
  • Predictive accuracy is < 4 cm position RMSE on 0.5 s rollouts even with 17–22 % parameter error — the dynamics fit is correct even when individual scalars drift.
  • Log-space parameterisation handles 7-OOM parameter scale spread (k_torque ~1e-10 vs mass ~1e-2) without per-param learning rates.
  • Phase 2 model mismatch (drag-bearing data, drag-less model): residual grows linearly with rollout horizon — the fitter cleanly produces a diagnosable, structured signal, not white noise.

Gotchas

  • Identifiability degeneracies are structural — mass/k_thrust and arm·k_thrust/I collapse to single ratios in the EOM. Look at the unconstrained recovery table: all three inertias hit the same percent error on every drone. The data only constrains ratios.
  • Constrained-fit position RMSE is sometimes higher than unconstrained because pinning mass + arm forces k_thrust to absorb more of the burden, drifting it further. Lower training loss ≠ better held-out accuracy.
  • Phase 2 dropped from gym-pybullet-drones to drag-enabled numpy_quad: the package wasn't on PyPI and a github install was unreliable. Drag-mismatch is a clean substitute (drag is unmodeled in our 8 params), but it understates the realism gap that PyBullet's full-physics engine would expose.
  • Phase 2 generator regenerated 23 / 200 training trajectories due to drag-induced divergence at high body rates — datasets are still clean but the action perturbation envelope is closer to its limits with drag enabled.

Barriers

  • None — both phases ran to completion.

Method

Grey-box system identification with privileged ground-truth params:

  1. Data generator: `NumpyQuadDynamics` rolls 200 training + 50 validation trajectories per drone (seeds 0 / 42). Action distribution is a mix of random-walk, sinusoidal sweeps, and step changes — chosen to cover translational, rotational, and bandwidth modes.
  2. Learner: `TorchVehicleParams` (8 scalars as `nn.Parameter`s, log-space) + `torch_quad` PyTorch port of the EOM. Sees only (state, action, next_state) tuples.
  3. Loss: K=20-step rollout MSE, std-normalized per state component. Adam (lr=1e-3), 500 epochs, batch 16.
  4. Two conditions: (a) Unconstrained — all 8 params learnable, init at ±50 % of truth. (b) Constrained — `mass` and `arm_length` pinned to ground truth (via `--fix`), simulating the realistic case where organisers publish nominal specs.

Phase 2 — model mismatch (drag-bearing data, drag-less model)

Phase 2 swaps the data generator: the same CF 2.1 drone, but now with elevated quadratic body drag (drag_coeff = [0.10, 0.10, 0.05], ~10× the numpy_quad default). Our 8-param grey-box torch_quad has no drag term, so this is a genuine model-mismatch test — the fitter has to absorb drag-induced effects into its 8 scalars.

Note: the original plan called for fitting against gym-pybullet-drones as the high-fidelity backend. The package isn't on PyPI and the GitHub install was unreliable in this env, so we pivoted to drag-enabled numpy_quad. The substance of the demo — characterising structural model mismatch — is the same.

Residual structure

The residual is predicted − target at each rollout step. A drag-induced bias would show as a velocity-correlated, monotonically-growing residual — visibly distinct from white-noise integration error.

RMSE (solid) and mean bias (dashed) per state group, averaged across held-out trajectories. Linear growth in position residual ≈ unmodeled drag deceleration accumulating.

Takeaways

  • The pipeline generalises across drone scales. Same code, same hyperparameters, no per-drone tuning — convergence on a 27 g micro behaves the same as on a 5 kg heavy lift.
  • Predictive accuracy ≫ parameter recovery accuracy. Worst-case parameter error is ~20 %, but Phase 1 position RMSE is 0.2–4 cm over 0.5 s rollouts. For model-based control, sim-to-sim transfer, or MPC, the dynamics are correct.
  • Pinning known scalars (mass, arm) is essentially free and consistently improves training fit. This is the realistic competition scenario when organisers publish nominal specs.
  • Model mismatch produces structured, diagnosable residuals. Phase 2's drag-bearing data, fit with a drag-less model, yields a position residual that grows linearly to ~23 cm over 0.5 s — distinct from white noise, exactly what unmodeled drag accumulating over time would look like. This means we can detect when our model is wrong and characterise how it's wrong.
  • For the AI Grand Prix sim-only qualifier, the first thing to check is whether the organiser's sim publishes drone parameters in a config file or exposes them via API. If yes, this whole sysID pipeline is a fallback — pin all 8 scalars and use the model directly. If no, run trajectories through the sim, collect telemetry, and fit. The pipeline shown here is ready for either case.
