**Symptom:** In the `monorace` conda env (Python 3.11, torch 2.5.1+cu121, RTX 3050 sm_86), any `dpvo.lietorch`/`lietorch` CUDA op (`SE3.exp`, inv, mul, …) crashes the process with `0xC0000005` (exit -1073741819). Instrumentation localized it EXACTLY to the async `<<<>>>` kernel-launch line in `exp_forward_gpu` (dispatch entered, output tensor allocated with valid device pointers, then the launch call itself host-AVs before returning). CPU path works perfectly.

**Ruled out by measurement (2026-07-13, do NOT re-litigate):**
- Compiler version — CPU works; MSVC 14.38 and 14.44 both crash.
- CUDA arch — cuobjdump confirms sm_86 SASS present in the fatbin.
- CUDA toolkit — system 12.1.105 (incomplete) AND a fresh complete conda 12.4 toolkit crash identically.
- torch / NVIDIA driver (592.27, unchanged since March/April) / cudart — torch's own CUDA (matmul) and a trivial custom CUDA kernel both work fine.
- Source — `dpvo/lietorch/src` was made byte-identical to pristine upstream `princeton-vl/lietorch@e7df865` (the `.type()`→`.scalar_type()` diff was necessary parity but NOT the cause).
- dtype/register pressure — float32 and float64 both crash.
- Kernel missing/misbuilt — cuobjdump shows `exp_forward_kernel<SE3<float/double>>` present with correct mangled names for sm_86.

**The discriminator:** a TRIVIAL custom CUDA kernel (built by the same toolchain via `load_inline`) launches fine; ANY Eigen-based lietorch kernel host-AVs at launch. So it's specific to the Eigen device-code kernels, and every measurable environment variable matches a state Alex says WORKED on 07-12.

**Key open question (only Alex knows):** what was the CUDA toolkit / env when it last worked? The system `nvcc.exe` CreationTime is 07-12 12:56 PM — the working standalone lietorch build (07-12 ~00:13) PREDATES it, so the morning build used a DIFFERENT nvcc than the system 12.1.105 that's now default.

**CONFIRMED ROOT CAUSE (2026-07-13, native stack trace via cdb/WinDbg):** The lietorch CUDA kernel **executes on the HOST CPU instead of launching on the GPU.** cdb caught the AV: `Attempt to read from address 0000000704000000` — which is EXACTLY the device pointer `a_ptr` (printed by instrumentation as `aptr=0000000704000000`). The faulting instruction (`lietorch_backends+0x27b2f`, in the exp launch path) dereferences a register holding that GPU address on the host. So the kernel *body* (`Tangent a(a_ptr + i*K)`) runs on the CPU and dereferences GPU memory → instant `0xC0000005`. That's why no toolkit/compiler/arch/dtype change ever helped (the kernel never reaches the GPU), why a trivial kernel survives, and why it worked on RunPod (Linux `<<<>>>` launches on GPU; this Windows build degenerates the launch into a host call). This is a **Windows CUDA codegen defect** specific to how this templated kernel's `<<<>>>` launch was built — NOT a version/config problem.

**VRAM fit — MEASURED 2026-07-13 (the old "4GB blocker" was a MISDIAGNOSIS):** With the sim running and GateNet out, **2182 MB is free**. DPVO static footprint (CUDA context + VONet + pre-allocated ring buffers) = **275 MB**; through frame 0 (feature extraction + cuDNN) = **407 MB**. The big buffers (fmap1/fmap2, patch maps) are fixed-size ring buffers already counted — they don't grow with frames. Steady-state peak realistically ~0.6–1 GB vs 2.18 GB free → **fits comfortably**. DPVO with PATCHES=32 at 640×360 is NOT VRAM-hungry; flights were always dying on the codegen bug, not memory. (True steady-state, frames 8+, unmeasurable locally because the forward crashes at frame 1's BA update on the codegen bug.)
